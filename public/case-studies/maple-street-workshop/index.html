Home/Case studies/Maple Street Workshop

A clearer path from curious visitor to confident inquiry.

A service-led website concept for an independent furniture workshop, built around useful project details, thoughtful photography, and a better first conversation.

Concept portfolio: fictional organizations and illustrative work, not commissioned client projects or measured business results.

Organization
Maple Street Workshop
Type
Independent furniture studio
Our proposed role
Content strategy, website design, front-end development
Project status
Self-directed concept / not a live client engagement

01 // THE STARTING POINT

A real-world problem, not a feature wishlist.

The starting scenario is a workshop whose best work lives on social media. Prospective customers see beautiful furniture, but cannot easily answer practical questions: what commissions are accepted, how a project begins, or what information to send. The owner ends up answering those same questions individually.

The guiding objective

Help a prospective customer understand the work and send a useful project inquiry.

The boundary: A small team needs to update projects without maintaining a complicated application.

02 // DISCOVERY & DIRECTION

Understand the journey before drawing the screens.

The concept starts with three customer journeys: a homeowner exploring a custom dining table, a designer looking for a fabrication partner, and a previous customer returning for care advice. Each needs different details, but all should be able to find a service explanation and a clear next step without knowing the workshop’s internal terminology.

The proposed site separates Work, Services, Our Workshop, and Start a Project. Project pages explain the brief, material choices, constraints, and finished details. Service pages explain the commission process before asking for an inquiry. Care information sits outside the sales journey so returning customers do not have to start over.

03 // DECISIONS THAT MATTER

Every detail has a job.

Make the work the evidence

Large project images sit beside concise explanations of the problem each piece solves. Instead of a gallery with no context, each project tells a short story about use, material, and craft.

Ask better questions, not more questions

The proposed inquiry flow asks for project type, approximate dimensions, timing, and contact details. Budget guidance is optional. Every field has a reason, and a successful submission would explain what happens next.

Keep editing predictable

A small set of page patterns gives the owner a repeatable way to add projects. Titles, cover images, captions, and project facts use consistent positions rather than requiring a new layout for every update.

04 // THE WORK, UP CLOSE

From a vague starting point to a clearer experience.

This comparison describes the fictional starting scenario and the proposed design direction. It is not a claim about an existing client website.

STARTING SCENARIO

  • A gallery with little explanation of the service.
  • A generic “Contact us” link after a long scroll.
  • Key project information scattered across captions.

PROPOSED DIRECTION

  • Project stories connect visual detail to customer needs.
  • A visible “Start a project” path from each service.
  • A consistent brief, materials, and process summary.

An inquiry that starts a useful conversation

Instead of “Tell us more,” the example brief asks: What would you like made? Where will it be used? Do you have approximate dimensions? Is there a date you are working toward? A short note explains that a rough idea is enough for a first conversation. This lowers the pressure without hiding the information the workshop needs.

What changes on a smaller screen?

Project photography moves above its supporting copy, while service details keep their natural reading order. The inquiry path stays easy to reach without covering the work. Captions and material notes remain text, not tiny labels baked into images.

05 // UNDER THE HOOD

Practical technology. Explicit boundaries.

The implementation approach uses a static-first page structure and reusable project records. Images have explicit dimensions, responsive sources, meaningful alternative text, and lazy loading below the first screen. Essential navigation and project content remain available without JavaScript. A real inquiry form would require a separately configured server-side endpoint with validation, spam controls, and clear delivery monitoring; this concept does not pretend to submit requests.

The awkward cases belong in the plan.

Long project names wrap naturally. Missing secondary photography does not leave an empty gallery. The inquiry confirmation and error states are part of the specification rather than last-minute additions. A honeypot alone would not be treated as sufficient protection for a live contact endpoint.

Verification plan

  • Review the critical journey on a small phone, tablet, and desktop.
  • Check keyboard order, visible focus, contrast, and meaningful image descriptions.
  • Exercise long content, missing optional fields, and invalid input states.
  • Verify every route, external destination, and recovery or escalation path.

This is the proposed acceptance checklist for the concept, not a report of a commissioned production release.

06 // DELIVERY & OWNERSHIP

Make the next update as considered as the first.

A polished launch is only part of the job. The proposed handoff explains what can be changed safely, what needs specialist help, and who owns the important accounts. Documentation should let a new maintainer understand the system without reconstructing the project from messages.

  • A page inventory and agreed content hierarchy.
  • Homepage, service, project, and inquiry layout specifications.
  • A reusable project-content checklist and image guidance.
  • A launch checklist covering links, metadata, form delivery, and ownership.

A sensible sequence

  1. Define: agree on the audience, scope, responsibilities, and acceptance criteria.
  2. Prototype: review structure, realistic content, and the critical interaction states.
  3. Build: implement the agreed patterns and record any decisions that affect maintenance.
  4. Validate: work through the checklist, resolve issues, and rehearse handoff.

07 // OUTCOMES WITHOUT THE GUESSWORK

Measure what matters. Don’t invent the numbers.

For a real launch, establish a baseline for inquiry quality, service-to-contact journeys, and avoidable clarification emails. Review anonymized patterns rather than collecting unnecessary personal data. A rise in raw submissions would not, by itself, prove that the design helped.

What this example demonstrates

The proposed structure, original interface illustration, content patterns, and implementation reasoning show how this project could be approached. No conversion uplift, revenue increase, saved hours, or client testimonial is claimed.

08 // THE TAKEAWAY

Clarity is a design feature.

A portfolio should do more than show that something looks good. Give the work enough context that a customer can recognize their own needs in it.
